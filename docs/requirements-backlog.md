# DomainHub 需求待办清单

> 本文件是后续实施提示词的可引用需求基线。每个条目使用稳定编号；后续可直接引用编号（例如 `DB-QUOTA-01`）。
>
> **冲突优先级：** 若本文件与 `docs/auth-design.md` 的账号安全、会话、RBAC、审计、数据约束或其他已定设计冲突，以 `docs/auth-design.md` 为准；本文件对应条目标记为“冲突待按 auth-design.md 校准”，不得自行覆盖安全约束。需求条目不代表已实现。

## 状态与阶段定义

- **已定稿**：产品规则已确定，可进入对应阶段设计/实现；不表示代码已完成。
- **待设计**：目标已确定，但算法、接口、数据结构、边界或验收细节仍需单独设计。
- **未开始**：尚未进入实现；依赖前置阶段完成并经确认。
- 阶段顺序固定为：账号体系 → 风控底座 → 只读域名列表 → 领取 → 用户中心 + 极简管理后台 → TG → DNS/Cloudflare → 支付/云服务器。

## A. 配额与反刷

### DB-QUOTA-01 — 不单独发放基础配额
- **所属阶段：** 风控底座（账号体系完成后）。
- **需求：** 新用户不再获得额外的 5 个基础名额；新用户唯一的注册基础奖励由 DB-QUOTA-02 定义为 +1。
- **依赖：** 账号体系；用户身份唯一性；配额账本 `quota_ledger`。
- **状态：** 已定稿（2026-11-01 站长最新决策，取代此前“基础 5 个名额”的旧规则）。
- **验收要点：** 邮箱注册和 GitHub 注册均不得额外发放基础 5 个名额；注册完成后基础注册奖励总计只能是 +1；邮箱验证不是另一笔独立奖励。历史账本不自动回删或追扣。

### DB-QUOTA-02 — 注册奖励
- **所属阶段：** 风控底座。
- **需求：** 完成有效注册并完成邮箱验证（或完成已验证邮箱的 GitHub OAuth 注册）后，奖励 +1 个二级域名名额。
- **依赖：** DB-QUOTA-01；账号体系中的注册完成/验证状态定义；quota_ledger。
- **状态：** 已定稿（2026-11-01）。
- **验收要点：** 邮箱验证仅作为注册完成条件，不另发奖励；邮箱注册和 GitHub OAuth 注册均只发放这一笔 +1；同一用户跨登录方式绑定、重复回调、重发验证码均不得重复入账。

### DB-QUOTA-03 — GitHub Star 奖励
- **所属阶段：** 风控底座（GitHub 外部事件接入）。
- **需求：** 用户完成 GitHub OAuth 账号绑定，并由服务端核实该 GitHub 用户已给 `shuji-chu/domainhub` 点 Star 后，奖励 +1 个二级域名名额。
- **依赖：** GitHub OAuth 身份绑定；指定仓库固定为服务端配置；可信 GitHub API 校验；quota_ledger。
- **状态：** 已定稿（2026-11-01）。
- **验收要点：** 不接受客户端自报；后端核实当前绑定的 GitHub 用户对指定仓库的 Star 状态；重复核验只能奖励一次；API 限流/不可用时显示“稍后重试”而不是误判成功；取消 Star 不自动扣回已到账奖励。

### DB-QUOTA-04 — TG 群与机器人奖励
- **所属阶段：** TG 阶段。
- **需求：** 用户绑定 Telegram 身份，并同时满足加入官方交流群、启动官方机器人两项条件后，奖励 +1 个二级域名名额；两项合计 +1，不拆成两份。
- **依赖：** TG 群与机器人固定配置；Telegram Bot API；账号与 TG 身份安全绑定；可信成员资格校验；quota_ledger。
- **状态：** 已定稿（2026-11-01；群 ID、群链接、机器人用户名由站长配置）。
- **验收要点：** 服务端通过 Bot API 核实群成员身份，并核实同一 Telegram 用户已启动机器人；两个条件都满足才奖励；重复加入、重复回调、重新绑定不得重复入账；退出群不自动扣回已到账奖励。

### DB-QUOTA-05 — 邀请真实新用户奖励
- **所属阶段：** 风控底座（邀请关系），在领取阶段前可用。
- **需求：** 邀请一名真实新用户并通过防刷校验后，邀请人奖励 +2 配额；累计邀请奖励不设上限，每名被邀请用户仅可贡献一次奖励。
- **依赖：** 账号体系；邀请关系模型；反刷规则 DB-QUOTA-07；quota_ledger。
- **状态：** 已定稿。
- **验收要点：** 被邀请人必须是此前不存在的真实新用户并完成邮箱验证；通过 DB-QUOTA-07 防刷校验后才入账；同一被邀请用户只能归属一个有效邀请关系，唯一幂等键确保奖励仅发放一次。邀请人累计奖励无上限，不代表放宽单个被邀请人的唯一性与反刷校验。

### DB-QUOTA-06 — 配额来源幂等键
- **所属阶段：** 风控底座。
- **需求：** 每一种配额来源必须有独立、稳定、可唯一约束的幂等键；至少覆盖基础配额、注册、GitHub Star、TG 群与机器人、邀请奖励。
- **依赖：** DB-QUOTA-08；各来源事件的稳定业务标识。
- **状态：** 已定稿。
- **验收要点：** 数据库唯一约束兜底；并发重复事件只产生一笔有效账本记录；幂等键不得由不稳定的请求时间戳临时生成。

### DB-QUOTA-07 — 邀请反刷规则
- **所属阶段：** 风控底座。
- **需求：** 邀请奖励需识别同 IP、同设备、同支付来源以及注册/行为时间过近等异常组合；命中规则的邀请不计奖励，并进入风险标记/复核流程。
- **依赖：** 账号体系设备/IP 风险信号；支付来源信号（仅可在支付阶段接入后启用）；风控规则与审计。
- **状态：** 待设计。
- **验收要点：** 不得仅凭单一共享 IP 自动认定作弊；明确阈值、时间窗口、误伤复核、证据留存和申诉处理；支付信号在支付阶段前不可假定存在。
- **冲突标注：** IP/设备数据采集与保留必须遵循 `docs/auth-design.md` 的隐私与最小化要求。

### DB-QUOTA-08 — quota_ledger 配额账本
- **所属阶段：** 风控底座。
- **需求：** 建立 `quota_ledger`，以追加式账本记录每笔配额增加、扣减、冻结、解冻或冲正；至少记录用户、变动量、来源类型、来源幂等键、关联对象、原因、创建时间和操作者/系统来源。
- **依赖：** DB-QUOTA-01 至 DB-QUOTA-07；审计基础。
- **状态：** 待设计。
- **验收要点：** 不直接覆盖历史余额记录；余额可由账本可靠汇总或通过受控缓存派生；唯一约束防止重复入账；管理员调整必须可追溯并写审计。

## B. 用户中心与极简管理后台

### DB-ADMIN-01 — 管理名额来源与数量
- **所属阶段：** 用户中心 + 极简管理后台。
- **需求：** 管理面板提供手动上架域名名额的入口，必须记录名额来源与数量，不允许无来源的隐式增加。
- **依赖：** 风控底座及 quota_ledger；管理角色/权限；审计。
- **状态：** 已定稿。
- **验收要点：** 每次手动上架写入账本与审计；可查询操作者、来源、数量、时间和原因。

### DB-ADMIN-02 — 配额规则变更权限
- **所属阶段：** 用户中心 + 极简管理后台。
- **需求：** 修改配额规则仅允许 `super_admin`；变更前后值、操作者、原因和时间必须写审计。
- **依赖：** RBAC；管理面板；审计。
- **状态：** 已定稿。
- **验收要点：** 默认拒绝未明确授权的操作；不能通过修改 `users.role` 获得权限。
- **冲突标注：** `docs/auth-design.md` 中 RBAC 关系表和权限矩阵优先；`users.role` 是废弃兼容字段，不得作为授权依据。

### DB-ADMIN-03 — 用户封禁与解封
- **所属阶段：** 用户中心 + 极简管理后台。
- **需求：** 管理员可按权限封禁/解封用户，记录原因、期限、操作者和审计事件。
- **依赖：** 账号状态模型；RBAC；审计。
- **状态：** 待设计。
- **验收要点：** 明确封禁范围、现有会话处理、申诉与解封流程；不得绕过账号安全规则。

### DB-ADMIN-04 — 配额调整
- **所属阶段：** 用户中心 + 极简管理后台。
- **需求：** 管理员可在授权范围内调整用户配额，必须通过 quota_ledger 记账并写审计。
- **依赖：** DB-QUOTA-08；RBAC；审计。
- **状态：** 已定稿。
- **验收要点：** 不允许直接修改账本历史；每次调整必须提供原因与来源；规则配置修改仍仅 super_admin 可执行。

### DB-ADMIN-05 — 订单查看
- **所属阶段：** 用户中心 + 极简管理后台（基础只读视图）；支付阶段补齐支付详情。
- **需求：** 管理面板可查看订单及其状态，按权限限制字段与操作；本条不授权提前实现支付。
- **依赖：** 订单数据模型（后续设计）；RBAC。
- **状态：** 待设计。
- **验收要点：** 先定义订单字段与脱敏规则；只读查看与支付状态修改严格分离。

### DB-ADMIN-06 — 域名状态查看
- **所属阶段：** 用户中心 + 极简管理后台。
- **需求：** 管理面板可查看域名状态、归属、风控标记、解析状态及相关事件；写操作按阶段和权限单独授权。
- **依赖：** 只读域名列表；领取阶段；风控底座。
- **状态：** 待设计。
- **验收要点：** 本条初始范围为查看，不提前授权领取、DNS 或 Cloudflare 写操作。

### DB-ADMIN-07 — 审计查询
- **所属阶段：** 用户中心 + 极简管理后台。
- **需求：** 提供受权限控制的审计查询，支持按操作者、目标、动作、结果、时间及关联对象筛选。
- **依赖：** `docs/auth-design.md` 审计分片/manifest/补偿链设计；RBAC。
- **状态：** 待设计。
- **验收要点：** 查询不得修改审计记录；补偿记录须明确标识并可追溯来源；不得暴露秘密、token 或不必要的个人数据。
- **冲突标注：** 审计字段、哈希链、分片封存、迟到事件补偿与归档策略一律以 `docs/auth-design.md` 为准。

## C. 邮箱功能解锁门槛

### DB-EMAIL-01 — GitHub Star 解锁域名配套邮箱
- **所属阶段：** DNS/Cloudflare（用户中心展示门槛可预留，实际 DNS/MX/TXT 配置仍按阶段顺序实施）。
- **需求：** 用户必须完成 GitHub OAuth 授权，并由服务端确认该 GitHub 账号已 Star 指定仓库，才允许在用户中心开启“域名配套邮箱”及配置相关 MX/TXT 记录。未满足条件时，前端提示“需 GitHub Star 解锁”；所有对应后端写接口必须独立校验并直接拒绝，不得依赖前端隐藏入口。
- **依赖：** GitHub OAuth 身份绑定；指定仓库配置；通过可信 GitHub API 或经验证的 webhook 查询/确认 Star 状态；DNS/MX/TXT 服务端授权策略。
- **状态：** 已定稿（产品门槛）；服务端 Star 状态校验与 DNS 接口接入待设计。
- **验收要点：** OAuth 账号必须绑定当前 DomainHub 用户；仅接受服务端验证的 Star 状态，不接受客户端传入的“已 Star”标记；未授权、取消 Star、API 校验失败或状态过期时默认拒绝；所有解锁/拒绝结果写审计。指定仓库使用服务端配置，不得由请求参数任意指定。本轮只更新规则文档，不实现 OAuth、Star 检查或 DNS/MX/TXT 写接口。

## D. 域名滥用治理

### DB-ABUSE-01 — 域名领取准入控制
- **所属阶段：** 风控底座（策略设计），在领取阶段启用。
- **需求：** 初始每个用户最多允许领取 3 个域名；同 IP + 同设备关联超过 3 个账号时标记风险；高风险后缀单独监控。
- **依赖：** 账号体系；设备/IP 风险信号；域名列表与后缀分类；领取阶段。
- **状态：** 已定稿。
- **验收要点：** “超过 3 个账号”按同 IP 与同设备组合判断；标记风险不等于自动永久封禁；初始额度与用户配额账本分开定义，二者关系需在领取设计中明确。
- **冲突标注：** 设备/IP 采集、存储、展示遵循 `docs/auth-design.md` 隐私最小化要求。

### DB-ABUSE-02 — 领取前黑名单检测
- **所属阶段：** 风控底座；领取阶段调用。
- **需求：** 领取前检查域名、用户、后缀及相关风险黑名单；命中规则时阻止领取或进入人工复核。
- **依赖：** 黑名单数据源与维护流程；域名只读列表；领取准入控制。
- **状态：** 已定稿。
- **验收要点：** 明确黑名单类型、更新方式、误判复核和审计记录；本条不实现领取业务。

### DB-ABUSE-03 — 每日 Web Risk 检测
- **所属阶段：** 风控底座。
- **需求：** 每日通过 Web Risk 检测域名风险，保存检测时间、结果、来源与处置状态。
- **依赖：** Web Risk 服务接入与密钥管理；域名库存；调度系统。
- **状态：** 待设计。
- **验收要点：** 明确 API 配额/费用、失败重试、结果过期、误报处理及外部服务不可用时的降级策略。

### DB-ABUSE-04 — 用户举报与上游 webhook
- **所属阶段：** 风控底座。
- **需求：** 接收用户举报和上游服务 webhook，统一进入风险事件队列并保留来源证据。
- **依赖：** 举报入口；上游 webhook 身份验证；事件去重；审计。
- **状态：** 待设计。
- **验收要点：** webhook 必须验签/鉴权、幂等去重、限流；举报不得直接触发不可逆处罚。

### DB-ABUSE-05 — 三层检测汇总与风险判定
- **所属阶段：** 风控底座。
- **需求：** 组合领取前黑名单、每日 Web Risk、举报与上游 webhook 三层信号，形成可解释的风险状态。
- **依赖：** DB-ABUSE-02、DB-ABUSE-03、DB-ABUSE-04。
- **状态：** 待设计。
- **验收要点：** 明确风险评分/规则优先级、冲突信号处理、证据保留和人工复核；每次状态变化写审计。

### DB-ABUSE-06 — 分级处置
- **所属阶段：** 风控底座；与领取、DNS 阶段联动。
- **需求：** 对达到阈值的风险事件可自动暂停解析、冻结配额；系统不得自动永久封禁用户或永久删除域名。
- **依赖：** 风险判定；配额账本；DNS/Cloudflare 控制面（暂停解析需在 DNS/CF 阶段实现）。
- **状态：** 已定稿。
- **验收要点：** 暂停解析与冻结配额必须可审计、可恢复；自动处置仅限可逆措施；永久封禁必须人工审核并具备申诉路径。

### DB-ABUSE-07 — 24 小时申诉窗口
- **所属阶段：** 风控底座（申诉流程设计），用户中心阶段提供入口。
- **需求：** 风险处置后提供 24 小时申诉窗口，用户可提交说明与证据，进入人工复核。
- **依赖：** 风险事件与处置记录；用户中心；管理后台复核权限。
- **状态：** 已定稿。
- **验收要点：** 明确 24 小时起算点、逾期处理、复核 SLA、复核人权限及恢复措施；自动可逆处置期间仍保留申诉能力。

## E. 免费托管与 DNS 自助管理

### DB-DNS-01 — 内置 DNS 记录管理
- **所属阶段：** DNS/Cloudflare。
- **需求：** 用户可自助管理 A、AAAA、CNAME、TXT、MX、NS 记录。
- **依赖：** 领取阶段域名归属模型；DNS/Cloudflare 服务层；权限校验。
- **状态：** 已定稿。
- **验收要点：** 仅允许操作本人拥有且状态允许的域名；定义各记录类型字段校验、冲突规则、TTL 与回滚方式。

### DB-DNS-03 — 根域名 TXT 校验后允许 CNAME
- **所属阶段：** DNS/Cloudflare。
- **需求：** 根域名必须先完成 TXT 所有权校验，校验通过后才允许配置 CNAME。
- **依赖：** DB-DNS-01；TXT 校验机制；域名归属模型。
- **状态：** 待设计。
- **验收要点：** 明确根域名判定、TXT token 生命周期、重复校验、校验撤销、CNAME 与现存记录冲突处理。
- **冲突标注：** 若与 `docs/auth-design.md` 的身份/安全校验要求冲突，以其为准。

### DB-DNS-04 — DNS 写操作限流与审计
- **所属阶段：** DNS/Cloudflare。
- **需求：** 所有 DNS 写操作实施限流并写审计；为 DNS API 预留 30 次/分钟的限流预算。
- **依赖：** DNS 服务层；限流策略；`docs/auth-design.md` 审计基础。
- **状态：** 已定稿。
- **验收要点：** 30 次/分钟是 API 预算上限设计值，仍需明确按用户、域名、IP 或 API key 的维度分配；失败与拒绝操作也要记录审计。
- **冲突标注：** 审计写入与失败关闭要求以 `docs/auth-design.md` 为准。

## F. 云服务器服务层

### DB-CLOUD-01 — DigitalOcean 内部服务层
- **所属阶段：** 支付/云服务器（在 DNS/CF 阶段之后）。
- **需求：** 将 DigitalOcean API 封装为 DomainHub 内部服务层；业务模块不得直接散落调用第三方 API。
- **依赖：** 云服务器产品设计；服务端密钥管理；订单/支付状态；审计。
- **状态：** 已定稿。
- **验收要点：** 对外只暴露内部受控接口；第三方 API 请求与响应进行必要脱敏；不得在本阶段连接或修改云服务器功能。

### DB-CLOUD-02 — DigitalOcean 密钥安全
- **所属阶段：** 支付/云服务器。
- **需求：** DigitalOcean 密钥仅保存在服务端秘密管理设施；采用最小必要 scope；前端、日志、数据库普通字段和仓库均不得出现密钥。
- **依赖：** 服务端部署与 secrets 管理；DigitalOcean 权限能力核对。
- **状态：** 已定稿。
- **验收要点：** 区分开发/测试/生产密钥；定期轮换；密钥泄露时可撤销；仓库只保留变量名与配置说明，不提交实际值。

### DB-CLOUD-03 — API 限流、重试、幂等与审计
- **所属阶段：** 支付/云服务器。
- **需求：** DigitalOcean API 调用必须有速率限制、退避重试、幂等保护和审计。
- **依赖：** DB-CLOUD-01、DB-CLOUD-02；订单/资源生命周期模型。
- **状态：** 待设计。
- **验收要点：** 对非幂等操作使用业务幂等键；区分可重试与不可重试错误；重试不得重复创建付费资源；日志脱敏。

### DB-CLOUD-04 — 云服务器付费开通
- **所属阶段：** 支付/云服务器。
- **需求：** 云服务器开通属于付费服务，不纳入免费域名名额或免费托管权益。
- **依赖：** 订单与支付；DigitalOcean 服务层；价格/资源规格设计。
- **状态：** 已定稿。
- **验收要点：** 只有订单支付成功且风控允许后才可开通；取消、退款、失败补偿规则另行设计；不得提供免费自动开通路径。

## I. 二级域名售卖与增值服务（商业化入口）

### DB-COMMERCE-01 — 用户中心增值服务入口
- **所属阶段：** 支付/云服务器（可在用户中心阶段预留只读入口定义）。
- **需求：** 用户中心提供“增值服务 / 购买域名”入口，产品体验对标传统 DNS 服务商；展示商品、价格、权益、订单状态和购买记录。本轮仅补充规则文档，不开发页面或购买接口。
- **依赖：** 用户中心；商品目录与定价；订单/支付；风控与审计。
- **状态：** 已定稿（入口与范围）；商品规格、定价和履约细节待设计。
- **验收要点：** 免费任务与付费商品分区展示；不得将付费商品伪装为免费领取任务；展示价格、支付网络、交付内容、退款/失败处理及限制。

### DB-COMMERCE-02 — 可售商品类型
- **所属阶段：** 支付/云服务器。
- **需求：** 增值服务商品包含三类：1）额外领取配额包；2）特定高级前缀的二级域名（例如短词、特定含义或稀缺前缀）；3）顶级域名代购服务。
- **依赖：** 商品目录、域名库存/可用性校验、配额账本、注册商/域名代购履约能力。
- **状态：** 已定稿（商品类别）；具体 SKU、库存锁定、定价、期限、续费和退款规则待设计。
- **验收要点：** 高级前缀商品必须在下单时锁定可售资源并明确具体域名；顶级域名代购须明确注册商、注册期限、实名/资料要求、续费责任及注册失败退款路径；不得承诺未确认库存或注册成功。

### DB-COMMERCE-03 — USDT 订单与支付交易模型
- **所属阶段：** 支付/云服务器。
- **需求：** 用户使用 USDT 支付。系统创建 Order 与 Payment 记录，分别承载商品订单生命周期和链上/支付通道交易生命周期；订单与支付状态不可混为一体。支付成功必须以服务端可信支付回调或链上确认规则为准，不能接受客户端自报成功。
- **依赖：** 支付服务商/链上网络接入；订单状态机；商品目录；风控；审计。
- **状态：** 已定稿（业务模型）；网络、确认数、汇率/定价、手续费、回调验签、退款及对账方案待设计。
- **验收要点：** 每笔交易记录订单号、Payment ID、币种 USDT、网络/链 ID、应付数量、实际到账数量、收款地址、交易哈希、确认数、支付状态和时间；回调验签、幂等去重、金额/币种/网络核对和异常告警必须由服务端完成。不得将待确认或金额不足的交易标记为已支付。

### DB-COMMERCE-04 — 付费履约与免费任务隔离
- **所属阶段：** 支付/云服务器。
- **需求：** 支付成功后按商品类型履约：配额包通过 quota_ledger 追加对应数量（使用订单级唯一幂等键）；高级前缀二级域名直接分配订单锁定的指定域名；顶级域名代购进入注册商代购履约流程。付费交易流与免费任务流完全隔离，免费注册/GitHub/TG/邀请奖励不得创建或伪造 Order/Payment，付费购买也不得伪造免费任务完成事件。
- **依赖：** DB-QUOTA-08；DB-COMMERCE-01 至 DB-COMMERCE-03；域名库存/分配；订单履约与补偿；审计。
- **状态：** 已定稿（隔离原则）；履约状态机与退款/冲正细节待设计。
- **验收要点：** 每个付费奖励以 order_id 为关联对象并通过稳定幂等键记账；域名分配只能发生在订单支付确认后；退款/拒付按独立冲正记录处理，不覆盖历史账本；免费任务奖励与付费购买必须使用不同 source_type、幂等键命名空间和审计 action。本轮不实现 USDT 支付、Order/Payment 业务或购买/分配代码。
